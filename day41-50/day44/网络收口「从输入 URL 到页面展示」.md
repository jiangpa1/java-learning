# 网络收口「从输入 URL 到页面展示」

以下是串联 9.16–9.19 网络核心知识的收口全景图：

---

### 第一步：DNS 解析（寻找 IP 地址）
*目标：把人类可读的域名解析为机器寻址的 IP。优先查缓存，查不到走递归/迭代。*

1. **查本地缓存（多级）**：
   - 浏览器缓存 -> 操作系统缓存（Hosts 文件） -> 本地路由器缓存。
2. **查本地 DNS 服务器（LDNS，递归查询）**：
   - 本机向配置的 LDNS（如电信运营商 DNS、`8.8.8.8`）发送请求。
3. **根域名与权威解析（LDNS 走迭代查询）**：
   - LDNS 查不到时，逐级询问：**根域名服务器**（`.`）  ->  **顶级域名服务器**（`.com`）  ->  **权威域名服务器**（`example.com`）。
   - 权威服务器返回该域名对应的 A/AAAA 记录，LDNS 缓存该记录并返回给客户端。
   - *(考点微补：DNS 通常基于 UDP 53 端口；若报文超过 512 字节或区域传输则走 TCP)*。

---

### 第二步：TCP 三次握手（建立可靠传输链路）
*目标：在不可靠的网络上，建立端到端、具备双向确认和序号同步的稳定连接。*

1. **第一次握手 (SYN)**：
   - 客户端生成随机初始序列号 $ISN = x$，发送 `SYN=1, seq=x`。客户端进入 `SYN_SENT` 状态。
2. **第二次握手 (SYN + ACK)**：
   - 服务端收到后，生成自己的 $ISN = y$，确认客户端序号，发送 `SYN=1, ACK=1, seq=y, ack=x+1`。服务端进入 `SYN_RCVD` 状态。
3. **第三次握手 (ACK)**：
   - 客户端确认服务端序号，发送 `ACK=1, ack=y+1, seq=x+1`。客户端和服务端均进入 `ESTABLISHED` 状态。
   - *(高频追问：为什么是三次？防止历史重复连接的初始化造成资源浪费；同步双方初始序列号；验证双向收发能力。第三次握手可以携带 HTTP 数据)*。

---

### 第三步：TLS 握手（建立安全通道，仅 HTTPS 触发）
*目标：通过「非对称加密协商对称密钥 + 数字证书验真」，实现机密性、完整性与身份认证。*

以主流的 **TLS 1.2 (ECDHE)** 为例（需 2 个 RTT；TLS 1.3 仅需 1 个 RTT）：
1. **Client Hello**：
   - 客户端发送：支持的 TLS 版本、加密套件列表（Cipher Suites）、客户端随机数 $Random\_C$。
2. **Server Hello & 证书下发**：
   - 服务端选定版本和加密套件，生成服务端随机数 $Random\_S$。
   - 发送 **数字证书**（包含服务端公钥，由 CA 机构私钥签名）。
   - 发送 **ECDHE 参数与签名**（`Server Key Exchange`），最后发 `Server Hello Done`。
3. **客户端证书验证 & 协商密钥**：
   - **验真**：客户端用系统内置受信任 CA 的根证书/公钥解密签名，验证证书有效期、域名、防篡改。
   - **密钥计算**：客户端发送自己的 ECDHE 参数（`Client Key Exchange`），双方利用 ECDHE 算法计算出共同的预主密钥（Pre-Master），再结合 $Random\_C$ 和 $Random\_S$ 生成一致的 **对称主密钥（Master Secret / Session Key）**。
   - 客户端发送 `Change Cipher Spec`（后续改用对称加密）和 `Finished`（附带握手报文的哈希校验）。
4. **服务端完成握手**：
   - 服务端同样发送 `Change Cipher Spec` 和 `Finished`。TLS 握手完成，后续全部采用**对称加密**传输。

---

### 第四步：HTTP 请求与响应（应用层数据交互）
*目标：浏览器请求资源，服务器处理并返回 HTML。*

1. **发送 HTTP Request**：
   - 包含请求行（Method, Path, HTTP 版本）、请求头（`Host`, `User-Agent`, `Cookie`, `Connection: keep-alive`）、请求体。
2. **服务器处理与反向代理**：
   - 请求通常先打到 Nginx（负载均衡、SSL 卸载），再打到后端应用集群（Tomcat/Go/RPC），查询 DB/Redis 完成业务逻辑组装。
3. **返回 HTTP Response**：
   - 包含状态行（`200 OK` / `304 Not Modified` / `301/302 Redirect` 等）、响应头（`Content-Type`, `Cache-Control`, `Set-Cookie`）、响应体（HTML 文本）。
   - *(考点微补：若启用 HTTP/1.1 默认 Keep-Alive，TCP 连接不立即断开，供后续静态资源复用；HTTP/2 则采用多路复用共用一个 TCP 连接)*。

---

### 第五步：浏览器解析与渲染（将代码转为像素）
*目标：主线程与渲染引擎解析返回的 HTML/CSS/JS，呈现最终可视画面。*

1. **构建 DOM 树**：
   - 词法/语法分析将 HTML 字节流解析为 Tokens，再转为 DOM 节点构造成 **DOM 树**。
2. **构建 CSSOM 树**：
   - 遇到 `<link>` 或 `<style>` 时解析 CSS，生成 **CSSOM 树**。*(CSS 不会阻塞 DOM 解析，但会阻塞渲染和后续 JS 执行)*。
3. **生成渲染树（Render Tree）**：
   - 结合 DOM 树与 CSSOM 树，过滤掉不可见节点（如 `<head>`、`display: none`），生成最终要绘制的 **Render 树**。
4. **布局计算（Layout / 回流 / 重排）**：
   - 计算 Render 树上每个节点在屏幕上的确切几何位置（X/Y 坐标）和大小（宽/高）。
5. **分层与绘制（Paint / 重绘）**：
   - 浏览器将页面划分为图层（Layers），调用绘图指令绘制各图层的颜色、阴影、背景等像素。
6. **显示（Composite / 合成）**：
   - 最终由合成线程（Compositor Thread）将各图层提交给 GPU，GPU 渲染后输出到显存并展示在显示器上。

---

### 💡 面试背诵绝杀句（总结收尾口径）

> “总的来说，这个过程可以概括为：**先通过 DNS 拿到 IP**，**经由 TCP 三次握手与 TLS 握手建立安全的加密信道**，接着**发送 HTTP 请求获取 HTML 数据**，最后由**浏览器内核解析生成 DOM 和 CSSOM，经过布局（Layout）与重绘（Paint）最终合成上屏**。”
