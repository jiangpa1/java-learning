# **① 先讲动机：一次网络读到底发生了什么**

调用 `read()` 后，数据要经历两步：
① 等待数据从网络到达内核缓冲区；
② 将数据从内核缓冲区拷贝到用户缓冲区。  



# **② 五种 IO 模型**

五种 IO 模型的差异，本质上只在于：**这两步分别由谁等待，进程等待时能不能做别的事。**

| IO 模型                                    | ① 数据准备：数据到内核缓冲区 | ② 数据拷贝：到用户缓冲区 |
| ------------------------------------------ | ---------------------------- | ------------------------ |
| 阻塞 IO                                    | 阻塞                         | 阻塞                     |
| 非阻塞 IO                                  | 不阻塞；反复轮询             | 阻塞                     |
| IO 多路复用（`select` / `poll` / `epoll`） | 阻塞等待“哪个连接可读”       | 阻塞                     |
| 信号驱动 IO                                | 不阻塞；内核就绪后发信号     | 阻塞                     |
| 异步 IO（AIO）                             | 不阻塞                       | 不阻塞；拷贝完成后通知   |

关键辨析：

> “同步 / 异步”看的不是阶段①，而是阶段②。
> 阶段②仍需要进程自己调用并等待 `read()` 完成的，属于同步 IO；只有 AIO 由内核完成拷贝后再通知进程，才是真正的异步 IO。

# **③ ⚠️ 经典混淆点：阻塞/非阻塞 ≠ 同步/异步**

**阻塞 / 非阻塞**描述的是：数据尚未准备好时，进程会不会被挂起。
**同步 / 异步**描述的是：数据从内核缓冲区到用户缓冲区这一段，进程是否需要主动参与并等待完成。  

所以，非阻塞 IO 只是“不在等数据时卡住”，但数据就绪后调用 `read()` 仍要等待拷贝完成，因此它依然属于**同步 IO**。
只有 AIO 由内核完成数据拷贝、完成后再通知进程，才是异步 IO。

# **④ select / poll / epoll 的区别**

| 对比项      | `select`                                    | `poll`                           | `epoll`                                     |
| ----------- | ------------------------------------------- | -------------------------------- | ------------------------------------------- |
| fd 数量限制 | 通常受 `FD_SETSIZE` 限制（Linux 常见 1024） | 无固定 API 上限，受系统资源限制  | 无固定 API 上限，受系统资源限制             |
| fd 数据结构 | 位图                                        | 数组                             | 红黑树（监听集合）+ 就绪链表                |
| 每次等待    | 用户态与内核态全量传递 fd 集合              | 同样需要全量传递                 | `epoll_ctl` 注册一次，`epoll_wait` 只等事件 |
| 找就绪 fd   | O(n) 扫描                                   | O(n) 扫描                        | 返回就绪队列中的事件，约 O(就绪事件数)      |
| 适用场景    | 少量连接                                    | 少量连接、突破 `select` 位图限制 | 大量长连接、高并发                          |

`epoll` 快的关键在于：不用每次把全部 fd 集合交给内核，也不需要在每次等待后扫描全部连接；驱动通知就绪时，内核把相应事件加入就绪队列，`epoll_wait()` 直接取出真正就绪的连接。

LT / ET 可以这样表述：

- **LT（水平触发，默认）**：只要缓冲区还有可读数据，就会持续报告“可读”。即使一次没读完，下次仍有机会处理，更稳妥。
- **ET（边缘触发）**：只在“从不可读变为可读”等状态变化时通知。收到事件后必须循环读取，直到返回 `EAGAIN` / `EWOULDBLOCK`；否则数据仍留在缓冲区、又没有新的状态变化，连接可能一直得不到再次处理。
- 因此，ET 通常必须搭配**非阻塞 fd**，避免“循环读到空”为止时反而卡住。

# **⑤ 🔗 收官：把三天串成一条链，讲透"Redis 单线程为什么快"**

> Redis 快，不是因为“单线程天然更快”，而是因为它把单线程用在了最适合的地方：
> 第一，数据主要在内存中操作，避免了磁盘访问这一高延迟路径；
> 第二，命令执行串行，通常不需要为共享数据加锁，也减少了线程调度、缓存失效等并发开销；
> 第三，它用 `epoll` 这类 IO 多路复用同时管理大量连接，网络等待不等于线程被一个连接阻塞。  
>
> 所以 Redis 的模型是：**单线程执行命令 + 事件驱动处理大量连接**。前提是单条命令足够快；一条慢命令会阻塞后续请求，这也是为什么生产中要避免 `KEYS` 等重操作。[Redis 官方说明](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

关于 Redis 6.0，可以补这一句：

> Redis 6.0 起可启用 IO 线程处理 socket 读写和命令解析，但**命令执行及数据修改仍由主线程串行完成**。这样提高网络吞吐，同时保留单线程执行带来的简单一致性语义；Lua 脚本正是利用了其执行期间不与其他命令交错的特性。[Redis 官方介绍](https://redis.io/blog/redis-8-0-m03-is-out-even-more-performance-new-features/)

避免说“单线程就没有上下文切换”——更准确是：**避免了多个执行命令的工作线程之间的切换与锁竞争**；系统调用、内核调度等仍然存在。





| OS / 网络概念        | 项目中的对应                                                 |
| -------------------- | ------------------------------------------------------------ |
| Redis 单线程命令执行 | Lua 脚本执行期间不会与其他命令交错，因此限流的“读计数 → 判断 → 写计数”可保持原子 |
| IO 多路复用          | Redis 用 `epoll` 等机制管理大量客户端连接；网络连接多，不代表需要为每个连接创建一个线程 |
| Java NIO             | Spring Boot 内嵌 Tomcat 默认通常使用 NIO Connector；在 Linux 上，JDK 的 `Selector` 会利用 `epoll` 一类系统能力 |
| `epoll` + 多进程     | Nginx 通常是 master 管理多个 worker；每个 worker 以事件循环管理大量连接，而非“一连接一线程” |
| 事件驱动             | 原生 WebSocket 的连接建立、可读、可写、关闭等都对应事件；具体由 Tomcat / Netty 等底层容器的事件循环调度 |

面试时可以把它串成：

> 我的限流依赖 Redis Lua 保证原子性；Redis 自身则通过 `epoll` 管理海量网络连接。应用侧的 Tomcat NIO、网关侧的 Nginx，以及 WebSocket 长连接，本质上也都在使用事件驱动和 IO 多路复用，让少量线程或 worker 服务大量连接。





#### 五种 IO 模型

先画“数据准备、数据拷贝”两阶段表。结论：只有 AIO 在两阶段都不需要进程等待；其余模型的数据拷贝阶段仍需进程等待，因此属于同步 IO。

#### `select` / `poll` / `epoll`

结论：高并发长连接优先 `epoll`。`select` / `poll` 每次都要传入并扫描全部 fd；`epoll` 注册一次，内核维护就绪队列，等待时返回真正就绪的事件。

#### `epoll` 的 LT 与 ET

结论：LT 安全、默认；ET 效率更高但要求更严格。LT 未读完会继续通知；ET 只在状态变化时通知，必须以非阻塞方式循环读到 `EAGAIN`，否则可能造成连接处理停滞。

#### 阻塞 / 非阻塞 vs 同步 / 异步

结论：前者看“数据没到时是否挂起”，后者看“数据拷贝是否由内核完成后再通知”。最大陷阱：**非阻塞 IO 仍属于同步 IO**
