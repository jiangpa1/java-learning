# 报文结构（请求行/头/空行/体）

你提到的“请求行 / 请求头 / 空行 / 请求体”是 **HTTP 请求报文（HTTP Request Message）** 的经典四段式结构。

这种结构是基于文本（ASCII）设计的，格式非常严谨。下面为你详细拆解每个部分的作用和格式：

---

### 报文整体结构图解

```text
+-------------------------------------------------------+
| 请求行 (Request Line)                                 |  <- 核心指令：干什么、找谁、用什么协议
+-------------------------------------------------------+
| 请求头 (Request Headers)                              |  <- 附加信息：客户端信息、数据格式等
| ...                                                   |     (由多行 Key-Value 组成)
+-------------------------------------------------------+
| 空行 (CRLF)                                           |  <- 关键分隔符：标志头部结束、内容开始
+-------------------------------------------------------+
| 请求体 (Request Body / Entity Body)                   |  <- 传输的数据内容 (可选)
| ...                                                   |
+-------------------------------------------------------+
```

---

### 详细拆解

#### 1. 请求行（Request Line）
位于报文的**第一行**，用来说明客户端想要执行的操作。它由三个字段组成，字段之间用**空格**隔开：
*   **请求方法 (Method)**：指示要进行的操作，常见的有：
    *   `GET`（获取资源）
    *   `POST`（提交数据/创建资源）
    *   `PUT`（更新资源）
    *   `DELETE`（删除资源）
*   **请求URL (Request-URI)**：告诉服务器要访问的具体资源路径（如 `/index.html` 或 `/api/users?id=1`）。
*   **HTTP版本 (HTTP Version)**：客户端使用的协议版本，常见的如 `HTTP/1.1` 或 `HTTP/2`。

> **示例**：`POST /api/login HTTP/1.1`

---

#### 2. 请求头（Request Headers）
位于请求行下方，由若干行组成。每行是一个键值对，格式为 **`Header-Name: Header-Value`**（冒号后通常跟一个空格）。它向服务器传递客户端的环境信息及对请求的约束。

常见的重要头部有：
*   `Host`: 目标主机名和端口号（HTTP/1.1 必须包含），例如 `Host: www.example.com`
*   `User-Agent`: 客户端的浏览器或操作系统信息。
*   `Accept`: 客户端能接收的数据类型，例如 `Accept: application/json`
*   `Content-Type`: **请求体**的数据格式（非常重要），例如 `Content-Type: application/json` 或 `application/x-www-form-urlencoded`
*   `Content-Length`: **请求体**的字节长度。
*   `Cookie` / `Authorization`: 用于身份验证的凭证。

---

#### 3. 空行（Empty Line）
*   **本质**：由一个回车符（CR，ASCII 13，`\r`）和一个换行符（LF，ASCII 10，`\n`）组成，即 `\r\n`。
*   **作用**：**极其重要**。它是 HTTP 协议的**法定分界线**。因为 HTTP 请求头的数量是不固定的，服务器在解析报文时，就是通过读取到这个“空行”来判断：“头部已经结束了，接下来如果有内容，那就是请求体”。
*   *注：即使没有请求体（如 GET 请求），这个空行也必须存在。*

---

#### 4. 请求体（Request Body）
空行之后的所有内容都是请求体。它包含了客户端实际要发送给服务器的数据。
*   **特点**：
    *   并不是所有请求都有请求体。通常 `GET`、`HEAD`、`DELETE` 请求没有请求体；而 `POST`、`PUT`、`PATCH` 通常带有请求体。
    *   内容格式不受限制，可以是普通的表单数据、JSON 字符串、XML、二进制数据（如上传的文件、图片）等。
    *   具体的格式必须与请求头中的 `Content-Type` 对应。

---

### 一个完整的 HTTP POST 报文实例

假设你正在登录一个网站，客户端向服务器发送的原始报文可能长这样：

```http
POST /api/v1/login HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Content-Type: application/json
Content-Length: 45
Accept: application/json

{"username": "zhangsan", "password": "123456"}
```

*拆解说明：*
1.  **请求行**：`POST /api/v1/login HTTP/1.1`
2.  **请求头**：从 `Host` 到 `Accept` 的 5 行内容。
3.  **空行**：`Accept: application/json` 下方的那一行空白。
4.  **请求体**：`{"username": "zhangsan", "password": "123456"}`

---

### 补充扩展：HTTP 响应报文（Response）
HTTP 的**响应报文**结构与请求报文高度对称，同样由四部分组成：
1.  **状态行 (Status Line)**：协议版本 + 状态码 + 状态描述（例如 `HTTP/1.1 200 OK`）
2.  **响应头 (Response Headers)**：如 `Server`, `Set-Cookie`, `Content-Type`
3.  **空行**：同样用于隔离头和体
4.  **响应体 (Response Body)**：服务器返回给浏览器的网页 HTML、图片数据或 JSON 结果。



# **请求方法语义**

HTTP 的**请求方法语义（Method Semantics）**，是指每种请求方法在设计之初被赋予的**“标准化意图”**。它告诉服务器：客户端发出这个请求，到底想对目标资源做怎样的操作。

在 RESTful 架构风格中，遵循方法的语义尤为重要。

---

### 一、 两个核心前置概念：安全与幂等

要真正理解方法语义，必须先理解这两个特性：

1. **安全性（Safe）**：
   * **定义**：该操作**只读**，不会改变服务器上的资源状态。无论调用多少次，数据库里的数据都不会变。
2. **幂等性（Idempotent）**：
   * **定义**：对同一个 URL 执行 **1 次** 和执行 **N 次**，**服务器上的资源最终状态是一模一样的**（$f(f(x)) = f(x)$）。
   * *注：幂等关注的是“服务器状态”，而不是返回的状态码（比如多次 DELETE 第一次返回 200，后面返回 404，但资源都是“不存在”的状态，它仍然是幂等的）。*

---

### 二、 常见请求方法的语义详解

#### 1. `GET` —— 获取资源
* **语义**：向服务器请求指定的资源（如网页、JSON 数据、图片等）。
* **特性**：**安全**、**幂等**、**可缓存**。
* **规则**：不能包含请求体（虽然协议未绝对禁止，但绝大多数代理和服务器会忽略）；参数应放在 URL（Query String）中。

#### 2. `POST` —— 处理/创建资源
* **语义**：向指定资源提交数据，通常会导致服务器**创建新资源**或**产生副作用**（如发送邮件、扣款）。
* **特性**：**不安全**、**不幂等**。
* **典型场景**：
  * 创建用户：`POST /users`（每调用一次，数据库就多一条数据）。
  * 提交表单、用户登录。

#### 3. `PUT` —— 替换/完整更新资源
* **语义**：用客户端发送的请求体，**全量替换**目标 URI 对应的资源。如果该资源不存在，有时也可用于创建该资源。
* **特性**：**不安全**、**幂等**。
* **典型场景**：
  * 修改用户资料：`PUT /users/123`（请求体必须包含该用户的完整最新数据。无论你提交覆盖 1 次还是 10 次，该用户的数据都是这套内容，因此是幂等的）。

#### 4. `PATCH` —— 局部修改资源
* **语义**：对目标资源进行**部分修改**（增量更新），只需提交发生变化的字段。
* **特性**：**不安全**、**通常非幂等**（依具体实现而定）。
* **典型场景**：
  * 只修改用户邮箱：`PATCH /users/123`，请求体为 `{"email": "new@example.com"}`。
  * *注：为什么非幂等？比如提交一个“在现有数组后追加一个元素”的 PATCH 操作，执行多次会追加多个元素。*

#### 5. `DELETE` —— 删除资源
* **语义**：请求服务器删除指定的资源。
* **特性**：**不安全**、**幂等**。
* **典型场景**：
  * 删除用户：`DELETE /users/123`（第一次删除了，之后再执行多次，该用户依然处于被删除状态，最终状态一致）。

#### 6. `HEAD` —— 获取报文头
* **语义**：与 `GET` 完全相同，但服务器**绝不能返回响应体**，只返回响应头。
* **特性**：**安全**、**幂等**。
* **用途**：
  * 检查资源是否存在（看返回 200 还是 404）。
  * 检查资源是否被修改过（比对 `ETag` 或 `Last-Modified`）。
  * 查看文件大小（通过 `Content-Length`），常用于大文件下载前的探测。

#### 7. `OPTIONS` —— 询问支持的方法
* **语义**：向服务器查询目标资源支持哪些 HTTP 方法，或者进行跨域检查。
* **特性**：**安全**、**幂等**。
* **典型场景**：
  * **CORS 预检请求**：现代浏览器在跨域发送复杂请求（如带 Token 的 POST）之前，会自动先发一个 `OPTIONS` 请求，询问服务器是否允许该跨域操作。

---

### 三、 经典语义辨析

#### 1. POST vs PUT 的区别
* **URI 的指代不同**：
  * `POST /users`：URI 指向的是“集合”，由服务器决定新资源的 ID 并创建它。
  * `PUT /users/123`：URI 指向的是“具体某一个资源”，客户端明确指定了要替换的对象。
* **幂等性不同**：
  * 连点两次提交按钮，`POST` 可能会生成两条相同的订单；而 `PUT` 多次提交只会覆盖更新，数据始终只有一份。

#### 2. PUT vs PATCH 的区别
* **全量 vs 局部**：
  * `PUT` 像**“替换”**：如果你提交 `{"age": 18}`，原有的 `name` 字段可能会被清空或重置为默认值。
  * `PATCH` 像**“打补丁”**：如果你提交 `{"age": 18}`，服务器只会把 `age` 改掉，保留原有的 `name`。

---

### 四、 方法特性速查表

| 方法 (Method) | 语义目标         | 安全 (Safe) | 幂等 (Idempotent) |  允许携带请求体  |  常见响应是否可缓存  |
| :------------ | :--------------- | :---------: | :---------------: | :--------------: | :------------------: |
| **GET**       | 读取资源         |   **是**    |      **是**       |   否（不推荐）   |        **是**        |
| **HEAD**      | 仅读取元数据(头) |   **是**    |      **是**       |        否        |        **是**        |
| **OPTIONS**   | 查询支持的能力   |   **是**    |      **是**       |        否        |          否          |
| **POST**      | 创建/处理数据    |     否      |        否         |      **是**      | 默认否（特殊配置可） |
| **PUT**       | 全量覆盖/替换    |     否      |      **是**       |      **是**      |          否          |
| **PATCH**     | 局部修改         |     否      |  否（标准定义）   |      **是**      |          否          |
| **DELETE**    | 删除资源         |     否      |      **是**       | 罕见（协议允许） |          否          |

> **总结口诀**：
> * 查数据用 **GET**（安全幂等带缓存）
> * 新增数据用 **POST**（不安全也不幂等）
> * 全量换用 **PUT**，局部改用 **PATCH**
> * 删数据用 **DELETE**，探虚实用 **HEAD/OPTIONS**



# **状态码**

HTTP **状态码（Status Code）** 位于响应报文的“状态行”中，由 **3 位数字**组成。它用来告诉客户端：**你的请求服务器收到了，处理结果究竟如何**。

HTTP 状态码按首位数字被严格划分为 **5 大类**：

| 首位数字 | 类别                      | 含义                                         | 常见生活比喻              |
| :------- | :------------------------ | :------------------------------------------- | :------------------------ |
| **1xx**  | 信息提示 (Informational)  | 请求已被接收，需要继续处理                   | “收到，正在办”            |
| **2xx**  | 成功 (Success)            | 请求已成功被服务器接收、理解、并处理         | “搞定了”                  |
| **3xx**  | 重定向 (Redirection)      | 需要后续操作才能完成，通常资源换位置了       | “去找另一个人/去别的地方” |
| **4xx**  | 客户端错误 (Client Error) | 客户端发出的请求有误（参数错、没权限等）     | “你给我的东西有问题”      |
| **5xx**  | 服务端错误 (Server Error) | 服务器处理请求时自己内部出错了（崩溃、超时） | “我（服务器）搞砸了”      |

---

### 一、 核心常见状态码详解

#### 1. 2xx 成功类（前端最喜欢的状态码）
* **`200 OK`**：最普遍的成功状态。GET 表示找到了数据，POST 表示操作成功并返回了结果。
* **`201 Created`**：请求成功且**服务器创建了新的资源**。通常是 `POST` 请求（如新增用户、发帖）成功的理想返回，常配合响应头 `Location` 指向新资源的 URL。
* **`204 No Content`**：请求成功，但**响应报文中不包含任何响应体**。常用于无需返回内容的 `DELETE` 或表单提交。
* **`206 Partial Content`**：断点续传或分块下载。表示服务器成功处理了带 `Range` 头的范围请求（视频播放拖进度条时最常见）。

#### 2. 3xx 重定向类（资源的搬迁与缓存）
* **`301 Moved Permanently`（永久重定向）**：
  * 资源已被分配了新的 URL，未来所有请求都应使用新 URL。
  * **搜索引擎（SEO）会将权重转移到新地址**，浏览器会强缓存该跳转。
* **`302 Found`（临时重定向）**：
  * 资源只是临时移动到了新地址，未来请求仍应访问原 URL（如：未登录时临时跳转到登录页）。
* **`304 Not Modified`（未修改 / 协商缓存命中）**：
  * **极为重要！** 客户端发起了带条件的请求（携带了 `If-None-Match` 或 `If-Modified-Since`），服务器比对后发现资源没变，告诉客户端：“直接用你本地的缓存吧”，**响应体为空，极大节省流量**。
* **`307 / 308`**：分别是 302 和 301 的严格版，**强制要求重定向时不得改变原请求的方法**（比如原来是 POST，跳过去还必须是 POST；而 301/302 历史遗留问题可能被浏览器改成 GET）。

#### 3. 4xx 客户端错误（开发日常排查核心）
* **`400 Bad Request`**：通用客户端错误。通常是发给后端的 JSON 格式错误、参数类型对不上或必填项缺失。
* **`401 Unauthorized`（未认证）**：
  * 名字叫“未授权”，**实际上是“未认证”**。表示“**你是谁？我不认识你**”。需要提供身份凭证（如缺失或失效的 Token/Cookie）。
* **`403 Forbidden`（已拒绝 / 权限不足）**：
  * 服务器知道你是谁，但**你没有权限访问该资源**。表示“**我知道你是张三，但这是管理员才能看的数据**”。
* **`404 Not Found`**：
  * 请求的资源在服务器上不存在。可能是 URL 拼写错误，或者该资源已被彻底删除。
* **`405 Method Not Allowed`**：
  * 请求方法不支持。例如后端接口只写了 `@PostMapping`，你却发了个 `GET` 请求。
* **`408 Request Timeout`**：客户端请求超时。
* **`409 Conflict`**：资源冲突。例如注册账号时，用户名已被占用。
* **`429 Too Many Requests`**：请求过于频繁，触发了服务端的**限流**保护机制（防刷、防爬虫）。

#### 4. 5xx 服务端错误（运维和后端背锅位）
* **`500 Internal Server Error`**：
  * 服务器内部代码报错（抛出了未捕获的空指针、语法错误、数据库崩溃等），最通用的后端 Bug 表现。
* **`502 Bad Gateway`（错误网关）**：
  * 作为网关或代理（如 Nginx）的服务器，从上游服务器（如 Tomcat/Node.js/PHP-FPM）接收到了一个无效的响应。**通常代表后端应用挂了、进程死掉了**。
* **`503 Service Unavailable`（服务不可用）**：
  * 服务器目前无法使用（由于超载或停机维护）。通常是临时的，稍后可能会恢复。
* **`504 Gateway Timeout`（网关超时）**：
  * 作为网关或代理的服务器，**等后端服务器响应等超时了**。常见原因：后端接口执行极慢（复杂 SQL、死循环、慢查询）拖垮了网关设置的超时阈值。

---

### 二、 高频面试/实战经典辨析

#### 1. 401 Unauthorized vs 403 Forbidden
* **401（身份问题）**：你没带工牌，或者工牌过期了，保安不让你进大门。（通过登录换取新 Token 即可解决）
* **403（权限问题）**：你带着有效工牌，证明你确实是公司员工，但你试图走进“财务室/机房”，保安拦下了你。（登录无法解决，需要管理员给你加权限）

#### 2. 502 Bad Gateway vs 504 Gateway Timeout
在现代 **Nginx 反向代理 + 后端应用** 的架构中极常见：
* **502**：Nginx 去连后端应用，发现后端应用端口**根本没启动，或者刚连上应用就崩溃退出了**（连接被拒绝/响应畸形）。
* **504**：Nginx 连上了后端，后端也接了请求，但是后端**一直在执行（比如卡死在 SQL 查询里），Nginx 设定的超时时间到了（如 60s），不等了**，直接甩给用户一个 504。

#### 3. 301 vs 302
* **301**：是“**搬家**”。浏览器和搜索引擎会记住新地址，下次用户在地址栏输入旧地址，浏览器根本不发请求给旧地址，**直接在本地内部转到新地址**。
* **302**：是“**出差住酒店**”。浏览器每次都得先去敲原地址的门，原地址再告诉它今天去哪里找。

---

### 三、 极简记忆口诀

* **200** 大吉大利（成功）
* **301** 搬家不回（永久重定向），**304** 没变读缓存
* **400** 参数传错，**401** 没登录，**403** 没权限，**404** 没找着
* **500** 后端报错，**502** 服务挂了，**504** 接口太慢跑超时

### 四、HTTP 状态码一律返回 200

业务状态放在响应体的 `code` 字段里。**这意味着鉴权失败、参数错误、服务器出错，HTTP 层看到的都是 200。**

拦截器（`setStatus(SC_OK)`）和异常处理器都遵循这个约定，保持一致。前端判断成功失败要看 body 里的 `code`。

这个选择本身没有对错，但**必须贯穿到底**——如果哪天有人给某个接口单独设了真实的 HTTP 状态码，前端的两套判断逻辑就会打架。

你所描述的这种设计，在业界被称为 **“HTTP 全 200 模式”**（或俗称“统一 200 约定”）。在很多国内的互联网公司、企业级管理系统（中后台）以及移动端/小程序开发中，**这种做法非常普遍，甚至一度成为某种“行业默认潜规则”**。

它的核心思想是：**将 HTTP 协议降级为纯粹的“传输通道”，把一切业务控制权移交到应用层（Body）**。

这种设计虽然用起来很爽（特别是对部分前端和业务开发来说），但它在架构体系上是一把典型的**“双刃剑”**。下面为你客观剖析它的**成因、代价**以及**工程上的妥协与建议**。

#### （1） 为什么很多团队喜欢“一律返回 200”？

团队选择这种模式，通常不是因为不懂 HTTP 协议，而是出于以下几个极其现实的工程原因：

1. **防止网关/运营商劫持与篡改**
   * *历史原因*：在早期的移动网络中，部分地区的电信运营商或老旧代理服务器，如果检测到非 200 状态码（如 404、500），会强行把响应体替换成运营商自己的“流氓报错页面”或广告。返回 200 可以骗过这些中间节点，安全把错误信息送达客户端。
2. **避免前端框架的“丑陋报错”与降级处理**
   * 像 `axios` 或浏览器的 `fetch`，默认遇到 4xx/5xx 会直接抛出异常并走 `catch` 分支。
   * 如果一律返回 200，前端网络层永远是 `resolve` 的，可以在统一的 Axios 响应拦截器（`interceptor`）中只针对 `response.data.code` 做一套逻辑判断，代码写起来非常平铺直叙。
3. **彻底避开 Web 容器的默认错误页**
   * 如果服务端发生未捕获异常抛出 500，Tomcat/Nginx 等可能会返回一段 HTML 格式的堆栈信息（Whitelabel Error Page）。这会导致前端 JSON 解析直接崩溃（`SyntaxError: Unexpected token < in JSON`）。
   * 全局异常拦截器强制 `setStatus(SC_OK)` 并返回统一的 `Result.fail(...)` JSON，能保证前端**百分之百能拿到格式规范的 JSON**。
4. **HTTP 状态码表达能力有限**
   * HTTP 状态码只有几十个，而实际业务场景中错误千奇百怪（如：`10001: 验证码错误`、`10002: 余额不足`、`10003: 账号被风控封禁`）。既然无论如何都要自定义业务 `code`，很多团队索性觉得“HTTP 状态码没有意义了，留一个 200 就行”。

#### （2） 这种做法的隐患与“副作用”（为什么架构师讨厌它）

虽然写业务代码方便了，但在**系统架构、基础设施和运维层面**，这种做法会带来毁灭性的破坏：

##### 1. 监控与告警全面“致盲”（最大痛点）
* 现代运维监控体系（如 Prometheus、SkyWalking、Datadog、Sentry、APM 工具）以及云厂商的负载均衡（SLB/ALB），**天生是基于 HTTP 状态码来统计服务健康度的**。
* 如果接口即使 NullPointerException 也返回 200，监控大盘上的 **“HTTP 错误率”将永远是完美的 0%**，报警系统形同虚设。你必须付出额外成本让监控系统去“深入解析每个请求的 Body”，这会极大消耗算力和带宽。

##### 2. 浏览器的调试地狱（DevTools 灾难）
* 打开 Chrome 开发者工具的 Network 面板：
  * **正常设计**：出错的接口红通通一片（401、500），一眼就能看出哪个接口炸了。
  * **全 200 设计**：所有的请求全是整齐划一的绿色 `200 OK`。开发排查问题时，必须一个个手动点开看 Response，效率极其低下。

##### 3. 熔断、降级与网关策略失效
* 微服务网关（如 Spring Cloud Gateway、Sentinel、Kong、Envoy）通常根据“下游服务的非 200 比例”来触发熔断保护。
* 如果下游服务不管怎么崩，给网关回的都是 200，网关会认为下游非常健康，继续疯狂转发流量，**直接导致服务雪崩而无法自动止损**。

##### 4. 无法利用网络基础设施的缓存
* CDN 和客户端缓存（如 HTTP 协商缓存 `304`）完全依赖 HTTP 状态码。
* 一旦错误响应也是 200，**CDN 可能会将一个“密码错误”或“服务器开小差”的错误响应缓存下来**，分发给后续所有正常用户。

---

#### （3）总结与最佳实践建议

* **如果你们是一个中小型业务团队、外包项目、或者基于微信小程序的系统**：
  采用“一律 200 + 业务 code”确实是**性价比极高、心智负担极低**的实用主义做法，没必要为了追求教条的 RESTful 而牺牲开发交付效率。
* **如果你们是大型微服务架构、有专业的 SRE 团队和严密的监控网关**：
  业界更推荐的 **现代最佳实践（双层机制）** 是：
  * **传输层与协议层对齐**：未登录就给 HTTP `401`，服务器崩了就给 HTTP `500`，传参不对就给 HTTP `400`。
  * **业务层保留详细 code**：在 400 的响应体里，依然返回 `{"code": 10002, "message": "密码必须包含大写字母"}`。
  * *这样兼顾了基础设施工具的透明识别，又满足了前端细粒度业务提示的需求。*

# **Content-Length vs Transfer-Encoding: chunked**

在 HTTP 协议中，`Content-Length` 和 `Transfer-Encoding: chunked`（分块传输编码）是**解决同一个核心问题**的两种互斥方案。

这个核心问题是：**在持久连接（Keep-Alive）复用同一个 TCP 连接时，接收方如何准确知道当前请求/响应的“包体（Body）在哪里结束”？**

如果没有明确的边界标识，接收方就不知道该读到哪里为止，可能会一直卡住等待（Hang 住超时），或者把下一个请求的数据误当成本次的数据。

---

### 一、 Content-Length（定长传输）

这是最传统、最直观的方式。

#### 1. 工作原理
发送方在发送 Body 之前，就已经知道了 Body 的**精确字节数**，并在请求头/响应头中明确标注。
* **流程**：
  1. 发送头：`Content-Length: 12`
  2. 发送一个空行 `\r\n`。
  3. 发送体：发送恰好 12 个字节的数据（如 `Hello World!`）。
  4. 接收方读满 12 个字节后，**立刻判定 Body 读取完毕**，连接可以继续接收下一个请求。

#### 2. 优缺点
* **优点**：
  * 简单直观。
  * 客户端可以预先知道文件总大小，从而**能够绘制精确的下载进度条**。
  * 易于做缓存。
* **致命缺点（针对动态内容）**：
  * 发送方**必须在发送任何 HTTP 报文之前，在内存中把整个 Body 完全生成出来**，才能算出长度。
  * 如果你在导出一个 2GB 的 Excel，或者后端需要执行耗时 10 秒的 SQL 才能把数据吐完，服务器就必须把这 2GB 数据在内存里全部攒齐，算好长度，然后才开始发第一个 HTTP 字节。这会导致**高内存占用**和**极高的首字延迟（TTFB）**。

---

### 二、 Transfer-Encoding: chunked（分块传输）

为了解决“数据还未生成完就想边算边发”的问题，HTTP/1.1 引入了分块传输编码。

#### 1. 工作原理
告诉接收方：“我不知道总共有多大，你也不要指望 `Content-Length` 了。我把数据切成一块一块（Chunk）发给你，**直到我发一个长度为 0 的块，就代表结束**。”

每个分块的严格格式为：
```text
[分块长度（16进制表示）] \r\n
[分块的二进制数据] \r\n
```

#### 2. 报文示例
假设服务器要分三批发送字符串 `"Hello "`、`"World!"`，报文如下：

```http
HTTP/1.1 200 OK
Content-Type: text/plain
Transfer-Encoding: chunked

6\r\n          <- 16进制的 6，表示后面有 6 个字节
Hello \r\n     <- 第一个数据块
6\r\n          <- 16进制的 6
World!\r\n     <- 第二个数据块
0\r\n          <- 长度为 0，代表整个 Body 彻底结束！
\r\n           <- 最后的空行
```

#### 3. 优缺点
* **优点**：
  * **流式传输（Streaming）**：后端产生一点，网络就吐出一点，无需在内存中缓冲整个响应。
  * **首字节响应时间（TTFB）极快**：建立连接后立即吐出响应头，大幅降低用户等待白屏时间。
  * **内存友好**：极大降低服务端/网关的内存压力（如大文件边读边发，几兆内存就能传输几十G文件）。
* **缺点**：
  * 客户端**无法预知总大小**，因此浏览器下载时通常**只能显示“已下载 XX MB”，而无法显示百分比进度条**。
  * 增加了微小的分块头开销（解析 16 进制长度与 `\r\n`）。

---

### 三、 核心区别与对照表

| 维度               | `Content-Length`                | `Transfer-Encoding: chunked`                                 |
| :----------------- | :------------------------------ | :----------------------------------------------------------- |
| **工作模式**       | 一次性定长                      | 动态分块、流式输出                                           |
| **总大小是否可知** | **是**（通过 Header 明确告知）  | **否**（必须读到 `0\r\n` 才知道结束）                        |
| **进度条支持**     | **支持**（前端能计算百分比）    | **不支持**（只能展示已下载大小）                             |
| **服务端内存压力** | 高（动态内容需全量缓冲在内存）  | 极低（零拷贝或小缓冲边读边发）                               |
| **典型适用场景**   | 静态资源（图片、CSS、固定文件） | **大模型流式打字机（SSE/AI）**、数据库大批量导出、动态生成的长 HTML、实时音视频流 |

---

### 四、 必须知道的“铁律”与安全陷阱

#### 1. 两者绝对不能共存（互斥原则）
* 根据 **RFC 7230** 规范：**如果一条消息中同时出现了 `Transfer-Encoding` 和 `Content-Length`，则 `Content-Length` 必须被完全忽略！**
* 原因：如果同时存在，各代理服务器对“以哪个为准”的实现可能不一致。

#### 2. 经典安全漏洞：HTTP 请求走私（Request Smuggling）
* 历史上最著名的攻击手段之一就是利用了这两个头。
* **攻击原理**：黑客在一个请求里**同时塞入** `Content-Length` 和 `Transfer-Encoding: chunked`。
  * 前端代理（如 CDN/Nginx）认为它是按 `Content-Length` 解析；
  * 后端服务（如 Tomcat/Node）认为它是按 `chunked` 解析；
* 两端对**报文边界的认知发生偏差**，导致黑客伪造的“下一个请求”被拼接到了正常用户的请求前，造成越权、凭证窃取等严重危害。

#### 3. HTTP/2 和 HTTP/3 中怎么办？
* 到了 **HTTP/2 和 HTTP/3**，这两种机制在传输层被**彻底革新**了：
  * HTTP/2 废弃了 `Transfer-Encoding: chunked`。
  * 它是基于**二进制帧（Frame）**的。数据直接装在 `DATA` 帧里，每个帧头上原生自带长度字段，最后一个帧会打上 `END_STREAM` 标记位表示结束。
  * 因此在 HTTP/2 中，天生具备流式传输能力，不需要在文本层拼接 16 进制的分块标记了。





# **Keep-Alive**

**HTTP Keep-Alive**（又称 **HTTP 持久连接 / Persistent Connection** 或 **长连接**）是 HTTP 协议中用于**复用底层的 TCP 连接**、大幅提升传输效率的一项核心机制。

---

### 一、 为什么需要 Keep-Alive？（背景与痛点）

在早期的 **HTTP/1.0** 中，通信默认是**短连接**的：
* 浏览器每请求一个网页、一张图片或一个 CSS，都要经历：
  1. TCP **三次握手**建立连接；
  2. 发送 HTTP 请求并等待响应；
  3. TCP **四次挥手**断开连接。
* **致命痛点**：
  * 一个现代网页通常包含几十个静态资源。如果每个资源都建立一次 TCP 连接，会造成**极高的延迟（RTT）**。
  * 服务器和客户端频繁分配、销毁套接字（Socket），消耗大量 CPU 和内存资源。
  * 破坏了 TCP 的**慢启动（Slow Start）**拥塞控制机制，每次传输都是在网络速度还没提起来时就掐断了。

```text
【短连接模式 (无 Keep-Alive)】
Client ---[三次握手]---> Server
Client ---[请求 html]---> Server
Client <---[响应 html]--- Server
Client ---[四次挥手]---> Server

Client ---[三次握手]---> Server  (又重新握手！)
Client ---[请求 css]----> Server
Client <---[响应 css]---- Server
Client ---[四次挥手]---> Server
```

---

### 二、 Keep-Alive 如何工作？

开启 Keep-Alive 后，客户端和服务器完成一次请求响应后，**不关闭 TCP 连接**，后续的 HTTP 请求可以**直接复用该通道**。

```text
【长连接模式 (开启 Keep-Alive)】
Client ---[三次握手]---> Server
Client ---[请求 html]---> Server
Client <---[响应 html]--- Server
Client ---[请求 css]----> Server  (直接复用！省去握手时延)
Client <---[响应 css]---- Server
Client ---[请求 js]-----> Server
Client <---[响应 js]----- Server
Client ---[四次挥手]---> Server  (全部传输完毕后才断开)
```

#### 版本演进差异：
1. **HTTP/1.0 时代（非标补充）**：
   * 默认是**关闭**的。
   * 客户端如果想开启，必须在请求头中显式加上：
     ```http
     Connection: keep-alive
     ```
   * 服务端如果也同意复用，在响应头中也必须带上 `Connection: keep-alive`。
2. **HTTP/1.1 时代（标准化默认开启）**：
   * 默认**全部开启**。你甚至不需要声明 `Connection: keep-alive`。
   * 如果任何一方（前端或后端）想彻底断开 TCP 连接，必须显式发送：
     ```http
     Connection: close
     ```

---

### 三、 经典面试考点：HTTP Keep-Alive vs TCP Keepalive

很多人会把这两者搞混，它们虽然名字极像，但**处于不同网络层，解决完全不同的问题**：

| 维度         | HTTP Keep-Alive（应用层）                      | TCP Keepalive（传输层）                              |
| :----------- | :--------------------------------------------- | :--------------------------------------------------- |
| **所在层次** | 操作系统应用层（OSI 7层）                      | 操作系统内核网络协议栈（OSI 4层）                    |
| **核心目的** | **连接复用**（省去握手挥手开销，提高传输速度） | **心跳保活与死链检测**（探测对方是否断网/死机）      |
| **工作机制** | 客户端/服务端商定不关 TCP 链路，持续发数据     | 在双方长期没数据传输时，内核自动发一个无数据的探测包 |
| **形象比喻** | “**别挂电话**，我还有别的问题接着问你。”       | “你还在听吗？**喂？还在不在？**”（检测对方挂了没）   |

---

### 四、 Keep-Alive 与 Content-Length 的强羁绊

这正好印证了我们前面讲的报文结构：
* 在**短连接**时代，服务器发完数据直接断开 TCP（发送 FIN 包），客户端读到连接结束（EOF）就知道数据接收完了。
* 但在 **Keep-Alive 开启后，TCP 连接不会断**。接收方怎么知道第一个请求的数据到哪里结束？下一个请求从哪里开始？
* **结论**：**Keep-Alive 的存在，强制要求 HTTP 报文必须具备明确的边界标记机制**——要么提供确切的 `Content-Length`，要么使用 `Transfer-Encoding: chunked`（分块编码）。否则会导致数据粘包或客户端永远挂起。

---

### 五、 Keep-Alive 的配置与工程权衡（生产注意点）

Keep-Alive 并不是越长越好。

* **隐患**：如果一个客户端连上服务器后就挂在那儿，什么都不发，而服务器傻傻地保持着 TCP 连接，那么成千上万个这样的连接会把服务器的**文件描述符（FD）和内存彻底耗尽**。
* **解决方案（超时与最大请求数）**：
  服务端通常会设置保活策略，在响应头中告知客户端：
  ```http
  Keep-Alive: timeout=5, max=100
  ```
  * `timeout=5`：如果这条连接空闲超过 5 秒没有任何新请求，服务器将主动关闭它。
  * `max=100`：复用这条 TCP 连接最多传输 100 次请求，满 100 次后服务器强制关闭它重新握手（防止内存泄漏）。

**在 Nginx 中的典型配置：**
```nginx
# 保持空闲连接的最大超时时间（默认通常为 65s 或 75s）
keepalive_timeout 65s;

# 单个 Keep-Alive 连接上允许处理的最大请求数
keepalive_requests 1000;
```

---

### 六、 总结与后来的演进

1. **HTTP/1.1 的遗憾**：
   虽然 Keep-Alive 复用了连接，但它是**串行**的——同一条 TCP 连接在同一时刻只能处理一个请求。如果前面的请求卡住了，后面的必须排队等待，这叫**线头阻塞（Head-of-Line Blocking）**。
2. **HTTP/2 的多路复用（Multiplexing）**：
   HTTP/2 真正意义上超越了单纯的 Keep-Alive。它通过在一条 TCP 连接上建立多个并行的“流（Stream）”，实现了真正的**并发传输**，彻底解决了 HTTP 层的线头阻塞。





# **HTTP 缓存**（`Cache-Control` / `ETag` / `Last-Modified`）

HTTP 缓存机制是前端性能优化、降低服务器负载和节省网络带宽的**最核心手段**。

整个 HTTP 缓存体系可以清晰地划分为两大阶段：**强缓存（本地直接读）** 和 **协商缓存（向服务器验证）**。

---

### 一、 缓存整体决策流程图

当你向浏览器请求一个资源时，遵循以下完整的判断链路：

```text
                  [发起请求]
                      │
            ┌─────────┴─────────┐
            ▼                   ▼
      【有本地缓存】       【无本地缓存】 ──────> 向服务器发请求 (200)
            │
            ▼
    [强缓存是否生效？] (检查 Cache-Control: max-age)
      ├── 是 ──> 直接读取本地缓存！不走网络 (200 from disk/memory cache)
      │
      └── 否 (已过期 / 声明了 no-cache)
            │
            ▼
    [发起协商缓存请求] (带上 If-None-Match / If-Modified-Since)
            │
      ┌─────┴────────────────┐
      ▼                      ▼
  【资源未改变】          【资源已修改】
      │                      │
  返回 304 Not Modified   返回 200 OK + 最新数据
  (告诉客户端继续用旧的)   (客户端覆盖旧缓存)
```

---

### 二、 第一阶段：强缓存（Strong Cache）

强缓存的特点是：**完全不与服务器通信**。浏览器直接检查本地缓存，如果没过期，直接使用。
（在浏览器开发者工具 Network 面板中显示为 `200 OK (from disk cache)` 或 `(from memory cache)`）。

控制强缓存的核心 Header 主要是 **`Cache-Control`**（HTTP/1.1 绝对主力）：

#### 1. `Cache-Control` 的常用指令（重点掌握）
* **`max-age=31536000`**：
  * 表示资源自请求之日起，在客户端**缓存有效的最大时间（单位：秒）**。在这个时间内，浏览器不会发起任何请求。
* **`no-cache`（极易被误解！）**：
  * **并不是“不缓存”**，而是**“跳过强缓存”**。
  * 含义：浏览器可以缓存这个资源，但**每次使用前，必须向服务器发起协商缓存请求**（去问服务器：“我的版本是最新的吗？”）。
* **`no-store`（真正的不缓存）**：
  * **禁止任何缓存**（既没有强缓存，也没有协商缓存）。浏览器和 CDN 绝不能存储该资源的任何副本，每次必须全量下载（常用于敏感金融数据）。
* **`public` vs `private`**：
  * `public`：所有节点（包括客户端和沿途的 CDN/代理服务器）都可以缓存。
  * `private`：只有客户端（终端用户的浏览器）可以缓存，中间 CDN 不允许缓存（如个人用户中心页面）。
* **`immutable`**：
  * 告诉浏览器：“这个文件这辈子都不会改了”。即使用户主动点击刷新（F5），浏览器也**不要向服务器验证**，直接读本地缓存（常用于带 Hash 值的 JS/CSS）。

> **历史遗留补充**：`Expires` 是 HTTP/1.0 的产物，代表一个绝对的过期时间点（如 `Expires: Wed, 21 Oct 2025 07:28:00 GMT`）。如果客户端本地时间被篡改，`Expires` 就会失效。**当 `Cache-Control: max-age` 和 `Expires` 同时存在时，`max-age` 具有绝对优先权。**

---

### 三、 第二阶段：协商缓存（Negotiation Cache / 条件请求）

当强缓存过期了，或者响应头标了 `Cache-Control: no-cache` 时，浏览器就必须向服务器发起**“条件请求（Conditional Request）”**，核对资源到底变了没有。

协商缓存有**两组成对出现的头**：

#### 1. 第一组：基于内容指纹（ETag / If-None-Match）—— **最精确**
* **第一次请求时**：
  * 服务器在响应头中带上文件的哈希/唯一特征值：
    `ETag: "5d8c72a5-b28"`
* **第二次请求（缓存过期后）**：
  * 浏览器在请求头中带上上次收到的指纹，问服务器：
    `If-None-Match: "5d8c72a5-b28"`
* **服务端比对**：
  * 如果文件内容没变，服务器返回 **`304 Not Modified`**，响应体为空！
  * 如果文件改动了，服务器返回 **`200 OK`** + 新的内容 + 新的 `ETag`。

#### 2. 第二组：基于修改时间（Last-Modified / If-Modified-Since）—— **传统保底**
* **第一次请求时**：
  * 服务器返回文件在操作系统上的最后修改时间：
    `Last-Modified: Tue, 12 Jan 2024 09:15:00 GMT`
* **第二次请求（缓存过期后）**：
  * 浏览器在请求头中自动带上这个时间：
    `If-Modified-Since: Tue, 12 Jan 2024 09:15:00 GMT`
* **服务端比对**：
  * 如果自该时间之后文件没有再改动过，返回 **`304 Not Modified`**。
  * 如果修改过，返回 **`200 OK`** + 最新文件。

---

### 四、 ETag 与 Last-Modified 深度对比

既然有了修改时间 `Last-Modified`，为什么 HTTP/1.1 还要发明 `ETag`？

| 维度         | `Last-Modified` (时间戳)                                     | `ETag` (内容哈希指纹)                         |
| :----------- | :----------------------------------------------------------- | :-------------------------------------------- |
| **精度**     | 只能精确到**秒级**                                           | **没有精度限制**（基于内容哈希）              |
| **误报场景** | 如果你打开文件只是编辑了一下加了个空格又删掉并保存，**内容没变，但修改时间变了**，会导致缓存失效。 | 内容没变，Hash 绝不会变，**不会误报**。       |
| **亚秒改动** | 1 秒内如果发生多次修改，时间戳无法察觉，会造成客户端读到脏数据。 | 能够完美感知。                                |
| **性能消耗** | 极小（只需读取文件系统的 metadata）                          | 需要计算哈希，消耗服务器部分 CPU              |
| **优先级**   | 低于 ETag                                                    | **高于 Last-Modified**（服务器优先校验 ETag） |

---

### 五、 现代前端生产环境最佳实践（终极方案）

在现代单页应用（Vue / React + Webpack / Vite）中，业界公认的**黄金缓存配置法则**如下：

#### 1. HTML 文件（入口文件：`index.html`）
* **配置策略**：**绝不走强缓存，走协商缓存**。
* **响应头设置**：
  ```http
  Cache-Control: no-cache
  ```
* **原因**：如果把 HTML 强缓存了 1 年，当你发布新版本时，用户永远无法察觉，因为用户根本不会向服务器请求新的 HTML，也就无法引用新的静态资源。

#### 2. JS / CSS / 图片（打包产物：`app.8f3a1b.js`）
* **配置策略**：**利用文件名内容哈希（Hash），开启极长强缓存**。
* **响应头设置**：
  ```http
  Cache-Control: max-age=31536000, immutable
  ```
* **协同工作原理**：
  * 当你改动了业务代码发布新版，Webpack 打包出来的 JS 文件名会变成 `app.9c2d4e.js`（指纹变了）。
  * 用户访问网站时，首先请求 `index.html`（因为是 `no-cache`，一定能拿到最新的 HTML）。
  * 最新的 HTML 中引用的是 `app.9c2d4e.js`，这是一个**全新的 URL**，浏览器直接发起全新下载，不受之前旧文件的强缓存影响。
  * 那些没改动的文件（如第三方库 `vendor.a67c.js`），因为文件名没变，直接秒读本地强缓存。

> **一句话总结**：**“HTML 永不强缓存（用 no-cache），带 Hash 的静态文件强缓存拉满（用 max-age=1年）”**。这是目前互联网各大厂兼顾极致速度与瞬间更新的标准模式。





# **Cookie / Session**

**Cookie** 和 **Session** 是为了解决同一个问题而诞生的：**HTTP 协议的“无状态（Stateless）”特性**。

HTTP 协议天生是“脸盲”的，每一次请求都是独立的，服务器无法仅仅通过 HTTP 协议本身识别出：“这次发帖的请求，和刚才登录成功的请求，是不是同一个用户发出的？”

为了记住用户状态，**Cookie** 和 **Session** 结成了一对经典搭档。

---

### 一、 通俗比喻与核心运作机制

* **Session（服务端）**：就像**健身房的前台档案库**。里面记录着：张三，VIP 8 级，余额 5000 元。
* **Cookie（客户端）**：就像**会员卡**。卡本身不记录你的余额，卡上只印着你的卡号（`SessionId: 10086`）。
* **协作流程**：你每次去健身房，只要把卡（Cookie）一刷，前台拿卡号去档案库（Session）里一查，就知道你是张三了。

#### 完整时序图

```text
客户端 (浏览器)                                服务端
     │                                            │
     ├───── 1. POST /login (账号: zhangsan) ────>│ (验证密码成功)
     │                                            │ 生成 Session 并存入内存/Redis
     │                                            │ SessionId = "abc-123"
     │                                            │
     │<──── 2. Set-Cookie: JSESSIONID=abc-123 ────┤ (响应头告知浏览器存卡)
     │                                            │
(浏览器自动把 Cookie 存入本地)                     │
     │                                            │
     ├───── 3. GET /user/profile ────────────────>│ (浏览器自动带上 Cookie!)
     │         Cookie: JSESSIONID=abc-123         │
     │                                            │ 服务端拿 "abc-123" 去查 Session:
     │                                            │ "哦！原来是张三，给他个人资料"
     │<──── 4. 200 OK (张三的个人资料) ────────────┤
```

---

### 二、 深入 Cookie：客户端的数据小抽屉

Cookie 是由**服务器生成，保存在浏览器本地**的一小段文本（每个域名通常限制 4KB 左右）。
只要没过期且符合条件，**浏览器每次发请求时，都会自动将该域名下的所有 Cookie 塞进请求头 `Cookie` 中带过去**。

#### 核心安全属性（前端/安全必考）：

服务端通过响应头 `Set-Cookie` 下发时，可以设置一系列参数，这些参数是防御黑客攻击的关键：

1. **`HttpOnly`（防御 XSS 攻击）**：
   * 标注了 `HttpOnly` 的 Cookie，**禁止通过 JavaScript 读取**（如 `document.cookie` 拿不到它）。
   * 作用：就算网站存在 XSS 漏洞被黑客注入了恶意脚本，黑客也**偷不走**你的登录凭证。
2. **`Secure`（防御中间人窃听）**：
   * 只有在使用 **HTTPS** 加密协议时，浏览器才会把这个 Cookie 发送给服务器；普通的 HTTP 协议不会发送。
3. **`SameSite`（防御 CSRF 跨站伪造请求攻击）**：
   * 限制第三方跨站请求时是否自动带上 Cookie。
   * `Strict`：严禁跨站携带。比如你从百度点一个链接进淘宝，不会携带淘宝的 Cookie（必须强制重新登录）。
   * `Lax`（现代浏览器默认）：允许导航类跨站携带（如点击普通链接跳转），但禁止图片加载、表单提交等跨站携带。
   * `None`：跨站无论如何都带（必须同时开启 `Secure`）。
4. **`Domain` 和 `Path`（作用域限制）**：
   * 决定 Cookie 在哪个域名和哪个路径下生效（例如设置 `Domain=.example.com`，则 `api.example.com` 和 `blog.example.com` 都能共享该 Cookie）。
5. **`Max-Age` / `Expires`（生命周期）**：
   * 不设置时默认为**会话级 Cookie（Session Cookie）**，关闭浏览器窗口即消失。
   * 设置了具体秒数（`Max-Age=3600`）后，写入本地磁盘，到期前无论怎么关浏览器都在。

---

### 三、 深入 Session：服务端的记忆中枢

Session 是在**服务器端**开辟的一块内存空间或持久化存储，用来存储用户的敏感信息（如用户 ID、角色列表、购物车内容等）。

#### 分布式架构下的 Session 痛点与破局

在单体单机架构中，Session 放在 Java/Node/Python 的进程内存里毫无问题。但在**微服务和集群架构**下：
* 用户第 1 次请求登录，打到了 **服务器 A**，Session 存在 A 上；
* 用户第 2 次请求查看资料，被负载均衡打到了 **服务器 B**，B 上根本没有这个用户的 Session，导致用户瞬间“被退登”。

**解决方案：**
* **反模式：Session 复制**（各服务器互相网内广播同步，极度浪费网络和内存，已被淘汰）。
* **现代标准方案：分布式 Session（Redis 集中存储）**：
  * 把所有服务器的 Session 全部剥离出来，统一塞进高速缓存 **Redis** 中。
  * 无论是服务器 A 还是服务器 B，都凭客户端带过来的 `SessionId` 去 Redis 查，完美实现无状态横向扩容。

---

### 四、 Cookie 与 Session 对比总览

| 维度         | Cookie                                                      | Session                                                 |
| :----------- | :---------------------------------------------------------- | :------------------------------------------------------ |
| **存储位置** | **客户端（浏览器）**                                        | **服务端（内存/Redis/数据库）**                         |
| **安全性**   | **较低**（存在客户端，有被篡改、XSS 偷取、CSRF 利用的风险） | **极高**（数据不出机房，客户端只有一个随机无规律的 ID） |
| **存储容量** | 极小（单条通常不超过 **4KB**，总数量有限制）                | 极大（取决于服务器/Redis 内存大小）                     |
| **数据类型** | 只能存 **字符串**                                           | 可以存 **任意对象/结构**（Java Object、字典等）         |
| **传输开销** | **增加网络带宽**（每次 HTTP 请求自动全量上传                |                                                         |
