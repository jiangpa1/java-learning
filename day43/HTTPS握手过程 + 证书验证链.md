# HTTPS握手过程 + 证书验证链

HTTPS 并不是一种全新的应用层协议，而是 **HTTP 运行在 TLS/SSL 加密安全传输层之上**（HTTP over TLS）。

它的底层核心是**混合加密体系**：
* **握手阶段**：使用**非对称加密**交换密钥、验证身份（解决信任问题，计算开销大）；
* **通信阶段**：使用协商出的**对称加密密钥**进行高速数据加密（解决性能问题）。

下面为你系统拆解：**TLS 握手全过程（以现代主流的 ECDHE 算法为例）** 和 **证书链的数学验真原理**。

---

### 一、 TLS 1.2 握手全流程图解（基于 ECDHE）

目前互联网最广泛使用的握手流程需要 **2 个 RTT（往返时延）**，总共经历“四步交互”：

```text
客户端 (Client)                                          服务端 (Server)
      │                                                        │
      │ ──────── 1. Client Hello (客户端打招呼) ──────────────> │
      │                                                        │
      │ <─────── 2. Server Hello + 证书 + 密钥交换 ─────────── │
      │                                                        │
[验证证书链，计算对称密钥]                                       │
      │                                                        │
      │ ──────── 3. Client Key Exchange + Finished ──────────> │
      │                                                        │
      │                                                [计算对称密钥]
      │ <─────── 4. Change Cipher Spec + Finished ──────────── │
      │                                                        │
================== 握手完成！进入加密通信阶段 ==================
      │                                                        │
      │ <====== 双向传输通过对称密钥加密的 HTTP 数据 (AES) ======> │
```

#### 详细步骤拆解：

#### 第 1 步：Client Hello（客户端发起）
客户端向服务端发送基础协商信息：
* **支持的 TLS 版本**（如 TLS 1.2、TLS 1.3）；
* **支持的密码套件列表**（Cipher Suites），例如告诉服务端：“我支持 `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`”；
* **客户端随机数（Client Random，记为 $R_c$）**：后续生成对称密钥的原材料之一；
* **SNI（Server Name Indication）**：告诉服务器客户端要访问哪个具体域名（方便单 IP 托管多域名的服务器匹配对应证书）。

#### 第 2 步：Server Hello & 凭证交付（服务端响应）
服务端收到后，回传一系列确认信息与身份凭证：
1. **Server Hello**：确认使用的 TLS 版本和选定的一套密码套件，并给出一个**服务端随机数（Server Random，记为 $R_s$）**。
2. **Certificate（核心）**：下发服务端的**数字证书链**（包含网站公钥、域名、机构签名等），供客户端审查身份。
3. **Server Key Exchange**：服务端临时生成一个椭圆曲线公钥参数（ECDHE 参数），并用自己的**证书私钥对其进行数字签名**（防止中间人篡改该参数）。
4. **Server Hello Done**：通知客户端“我第一阶段的话讲完了”。

#### 第 3 步：客户端验证、密钥协商与收尾
客户端收到服务端的证书和参数后：
1. **验证证书链**（见下文第二节，若证书伪造或过期，直接弹红告警中断连接）；
2. 确认合法后，客户端也临时生成一个椭圆曲线公钥参数，通过 **Client Key Exchange** 发送给服务端；
3. **推导对称密钥**：
   * 客户端利用 ECDH 算法，结合服务端的公钥参数与自己的私钥参数，计算出一个**预主密钥（Pre-Master Secret）**。
   * 此时客户端手里集齐了三个要素：$R_c$ + $R_s$ + Pre-Master Secret。客户端将它们结合，生成最终通信用的**主对称密钥（Session Key）**。
4. **Change Cipher Spec**：通知服务端：“后面的话我都要用刚刚算出的对称密钥加密了”。
5. **Finished（Encrypted Handshake Message）**：把前面所有握手交互的数据做个哈希并用对称密钥加密发给服务端，用于校验握手过程是否被黑客中途篡改。

#### 第 4 步：服务端收尾
1. 服务端收到客户端的 ECDHE 公钥参数，同样通过算法算出完全一致的 **Pre-Master Secret**；
2. 服务端利用手里同样的 $R_c$ + $R_s$ + Pre-Master Secret，推导出**完全相同的 Session Key**；
3. 服务端解密客户端的 Finished 报文，校验无误；
4. 服务端也回应 **Change Cipher Spec** 和 **Finished**；
5. **握手圆满结束**，后续发送的 `GET / HTTP/1.1` 全部用 Session Key 对称加密。

### 二、 核心机制：数字证书与证书信任链

在握手过程中，客户端如何确信“和我对话的确实是百度/腾讯，而不是隔壁老王搭建的中间人代理”？答案就是**数字证书信任链（Web PKI）**。

#### 1. 证书里装了什么？
由权威机构（CA，Certificate Authority）颁发的数字证书，本质上包含两大部分：
* **明文信息部分**：
  * 该网站的**公钥（Public Key）**
  * 绑定的域名（如 `*.baidu.com`）
  * 证书所有者信息、有效期
  * 颁发者（CA）的信息
* **CA 的数字签名（Signature）**：
  * CA 机构用自己的**私钥**，对上述明文信息的哈希值加密后生成的密文。

---

#### 2. 证书信任链结构（从根到叶）

现实中，绝不会由最高级的根证书直接给千千万万个小网站发证书，而是形成了一个**层层背书的树状链条**：

```text
[根 CA 证书 (Root CA)]        <- 内置在操作系统/浏览器底层（信任锚点，自签名）
        │ (签发/担保)
        ▼
[中间 CA 证书 (Intermediate CA)] <- 提高安全性，若出事故只需吊销中间 CA，无需换根
        │ (签发/担保)
        ▼
[服务器实体证书 (Leaf Certificate)] <- 网站购买部署的证书 (如 baidu.com)
```

---

#### 3. 数学原理：浏览器如何验真（自下而上回溯）

当浏览器拿到网站发送过来的“服务器证书”时，校验过程如下：

```text
               ┌──────────────────────────────┐
               │    服务器实体证书 (明文数据)     │
               └──────────────┬───────────────┘
                              │ Hash 计算
                              ▼
                       [ 计算出摘要 A ] 
                              │
                    比较 A 和 B 是否绝对一致？
                    ├── 是：证书内容未被篡改！
                    └── 否：证书无效，弹出严重警告！
                              ▲
                       [ 解密出摘要 B ]
                              │
               ┌──────────────┴───────────────┐
               │  上一级(CA)的【公钥】解密签名   │
               └──────────────▲───────────────┘
                              │
               ┌──────────────┴───────────────┐
               │    服务器实体证书中的【CA签名】 │
               └──────────────────────────────┘
```

1. **第一层验真（验证服务器证书）**：
   * 浏览器把服务器证书的明文拿出来，用指定的 SHA-256 算法算出一个哈希值（**摘要 A**）。
   * 浏览器找到发证方（中间 CA）的证书，拿出**中间 CA 的公钥**，去解密服务器证书里的**数字签名**，得到一个解密后的哈希值（**摘要 B**）。
   * 如果 **摘要 A == 摘要 B**，数学上证明两件事：
     1. 该证书内容确实**没有被中间人篡改过**（哪怕改动一个标点，哈希值都会天差地别）；
     2. 该证书确实是由这个**中间 CA 亲手签发的**（因为只有中间 CA 的私钥才能生成这个签名）。

2. **第二层递归验真（验证中间 CA 证书）**：
   * 浏览器紧接着会问：“谁来证明这个中间 CA 是合法的？”
   * 浏览器顺着证书链往上走，用**根 CA（Root CA）的公钥**，按照同样的方法解密中间 CA 的签名，验证中间 CA 的合法性。

3. **终极信任锚点（信任从何而来？）**：
   * 递归到了**根证书（Root CA）**，根证书是自己签发自己的（Self-signed）。
   * 此时浏览器不需要向上验证了，因为 **权威根证书已经被操作系统厂商（微软 Windows、苹果 iOS/macOS、谷歌 Android）或浏览器（Chrome/Firefox）在出厂时强制预装在操作系统的受信任根证书库（Trust Store）中了**。
   * 只要链条能够最终追溯到系统受信任的根，验证宣告成功。

#### 4. 除了数学签名，浏览器还会做的“附加体检”：
* **域名是否匹配**：证书里的 Subject Alternative Name (SAN) 是否涵盖当前访问的域名；
* **有效期检查**：当前系统时间是否在 `Not Before` 和 `Not After` 之间；
* **吊销检查**：通过 **CRL（证书吊销列表）** 或 **OCSP（在线证书状态协议）** 查询该证书是否曾因私钥泄露被站长提前吊销。

### 三、 延伸：TLS 1.3 带来了什么革命性改进？

现代的 **TLS 1.3** 相比 TLS 1.2 做出了极具颠覆性的重构：
1. **握手提速（从 2-RTT 砍到 1-RTT）**：
   * TLS 1.3 在 `Client Hello` 发起的第一步，就直接“猜测”服务端偏好的算法，把自己的 ECDHE 公钥参数**一并打包发过去**。
   * 服务端收到后一步到位算好密钥，直接回传 `Server Hello + Finished`。握手时间直接减半（仅需 1 个往返即可开始发业务数据）。
   * 支持 **0-RTT（早前会话复用）**，二次访问时甚至第一包请求就带上加密数据。
2. **强制前向安全（Forward Secrecy）**：
   * 彻底**废除了传统的 RSA 密钥交换算法**（老 RSA 模式下，如果服务器私钥在未来某天泄露，黑客把历史抓包全部拿出来都可以被破解）。
   * TLS 1.3 强制只支持 ECDHE 等临时密钥协商算法，即使私钥未来泄露，历史流量也永远无法被解密破解。
